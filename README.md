# Mini CRM: «Объекты и задачи»

Небольшая CRM для строительной компании. Постановщик ставит задачи по объектам (стройкам), исполнители выполняют их и отправляют на проверку.

**Демо:** <ВСТАВЬТЕ_ССЫЛКУ_VERCEL>

## Тестовые доступы

| Роль | Email | Пароль    |
|---|---|-----------|
| Постановщик | manager@test.local | Exec123!  |
| Исполнитель 1 | exec1@test.local | exectest1 |
| Исполнитель 2 | exec2@test.local | exectest2 |

## Стек

- React + TypeScript + Vite
- Tailwind CSS, lucide-react, sonner
- TanStack Query, React Router
- Supabase (Postgres, Auth, RLS)

## Возможности

- Две роли: постановщик и исполнитель.
- Объекты (название, адрес) и задачи по объектам.
- Цикл статусов: Новая → В работе → На проверке → Принята / На доработке → В работе.
- История каждой смены статуса: кто, когда, из какого статуса в какой, комментарий.
- Экран «Мои задачи» для исполнителя.
- Интерфейс показывает только действия, доступные текущему пользователю в текущем статусе.

## Как запустить локально

### 1. Установка

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd mini-crm
npm install
```

### 2. Проект Supabase

1. Создайте проект на [supabase.com](https://supabase.com) (бесплатного тарифа достаточно).
2. Откройте **SQL Editor** и выполните файл `supabase/migrations/20260101000000_init.sql` целиком.
   Он создаёт таблицы, триггеры, функцию смены статуса и политики доступа (RLS).
   (Альтернатива: `supabase link` и `supabase db push`.)
3. **Authentication → Sign In / Providers → Email**: выключите **Allow new users to sign up**.
   Открытая регистрация должна быть отключена.
4. **Authentication → Users → Add user** (с галочкой *Auto Confirm User*): создайте трёх пользователей:
   `manager@test.local`, `exec1@test.local`, `exec2@test.local`.
5. Назначьте роль постановщика и имена в SQL Editor:

```sql
update public.profiles set role = 'manager', full_name = 'Имя Постановщика'
where id = (select id from auth.users where email = 'manager@test.local');

update public.profiles set full_name = 'Имя Исполнителя 1'
where id = (select id from auth.users where email = 'exec1@test.local');

update public.profiles set full_name = 'Имя Исполнителя 2'
where id = (select id from auth.users where email = 'exec2@test.local');
```

По умолчанию каждый новый пользователь получает роль `executor`. Роль `manager` выдаётся только вручную.

### 3. Переменные окружения

```bash
cp .env.example .env
```

Заполните `.env` значениями из **Project Settings → API**:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=<anon public key>
```

Используется только публичный `anon`-ключ. Ключ `service_role` во фронтенд и в репозиторий не попадает.

### 4. Запуск

```bash
npm run dev      # режим разработки
npm run build    # production-сборка
```

## Тесты безопасности

Файл `supabase/tests/security_tests.sql` проверяет правила доступа прямо в базе, в обход интерфейса.

Как запустить: после миграции и создания трёх тестовых пользователей откройте SQL Editor, вставьте файл целиком и выполните. Тесты идут в транзакции с `rollback`, данные в базе не остаются.
Успех: в сообщениях только `OK: ...` и итог `ALL TESTS PASSED`.

Что проверяется:

- исполнитель видит только свои задачи и объекты, где у него есть задачи;
- нельзя читать и менять чужие задачи, в том числе напрямую и через RPC;
- запрещённые переходы статусов не проходят;
- исполнитель не может принять свою задачу, постановщик не выполняет шаги исполнителя;
- возврат на доработку без комментария невозможен;
- историю нельзя подделать, изменить или удалить;
- нельзя повысить себе роль, создавать объекты и задачи, удалять задачи (для исполнителя).

## Как устроена защита

Правила доступа работают на уровне базы, а не только в интерфейсе.

- **RLS** включён на всех таблицах: `profiles`, `objects`, `tasks`, `task_history`.
- **GRANT на уровне колонок**: клиент не может писать в `status`, `author_id`, `created_at`.
- **Смена статуса только через функцию** `change_task_status` (`security definer`). Она проверяет роль, назначение исполнителя, допустимость перехода и обязательный комментарий. Прямой `update` статуса блокируется триггером.
- **История** (`task_history`) доступна клиентам только на чтение. Записи создаёт только база: при создании задачи и при смене статуса.
- **Регистрация отключена**, пользователей создаёт администратор.
- **Секретных ключей** в репозитории нет.

## Структура проекта

```
src/
  components/      layout (AppLayout, Sidebar) и общие ui-компоненты
  features/
    auth/          вход, RequireAuth, RequireRole
    objects/       список и карточка объекта
    tasks/         задачи, действия по статусам, история
  lib/             клиент Supabase, форматирование, queryClient
supabase/
  migrations/      SQL-миграции (схема, RLS, функции)
  tests/           тесты безопасности (запускаются вручную)
```

## Деплой

Приложение развёрнуто на Vercel. В настройках проекта заданы переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Файл `vercel.json` перенаправляет все пути на `index.html`, чтобы работали прямые ссылки и обновление страницы.
