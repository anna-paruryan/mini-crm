# Решения и допущения

## Решения, которые я принял сам (ТЗ не давало однозначного ответа)

**Роли и пользователи**
- Любой новый пользователь автоматически получает роль «исполнитель». Роль «постановщик» выдаётся только вручную в базе, чтобы нельзя было повысить себя через интерфейс или API.
- Исполнителем задачи может быть только пользователь с ролью «исполнитель». Это проверяется в базе.
- Профили (id, имя, роль) читают все вошедшие пользователи: это нужно, чтобы показывать имена исполнителей и авторов. Email в профили не копируется, в поле имени хранится нормальное имя.

**Задачи**
- Постановщик может редактировать задачу и менять исполнителя в любом статусе, включая «Принята».
- Задачу можно создать без исполнителя, но взять её в работу тогда некому, пока исполнитель не назначен.
- Постановщик не выполняет шаги исполнителя («взять в работу», «отправить на проверку»), даже если он видит все задачи. Переходы строго по таблице из ТЗ.
- Автор и дата создания задачи не меняются после создания.
- Задача создаётся только в статусе «Новая». Создание записывается в историю первой записью (из статуса «пусто» в «Новая»).
- Комментарий при смене статуса ограничен 2000 символами, обязателен только при возврате на доработку.

**Безопасность**
- Защита двойная: права на уровне колонок (GRANT) и политики строк (RLS). Если одна сломается, вторая остаётся.
- Статус меняется только функцией `change_task_status`. Прямое изменение статуса блокируется триггером.
- Историю клиент может только читать. Записи создаёт только база, изменить или удалить их через API нельзя.
- Если исполнитель обращается к чужой задаче, база отвечает «Задача не найдена», а не «нет прав». Так не раскрывается, что такая задача существует.
- Исполнитель видит объект, только если в нём есть его задача.
- Во фронтенде используется только публичный `anon`-ключ. Ключ `service_role` нигде не хранится.
- Открытая регистрация отключена в настройках Supabase, пользователей создаёт администратор.

## Что не успел или сделал упрощённо

- **Удаление задачи удаляет и её историю** (каскадное удаление). Подделать историю через API нельзя, но постановщик может удалить задачу целиком. Для production лучше «мягкое удаление» (пометка вместо стирания) или запрет удаления задач с историей.
- **Удаление объекта** запрещено, пока в нём есть задачи (защита от потери данных).
- **Нет самостоятельного создания пользователей и смены ролей в интерфейсе.** Это делает администратор в панели Supabase.
- **Нет восстановления пароля**, уведомлений и вложений к задачам.
- **Нет пагинации и поиска** в списках. Для небольшого объёма данных это не требуется.
- **Автоматических тестов фронтенда нет.** Правила безопасности проверяются SQL-тестами (`supabase/tests/security_tests.sql`).
- **Новые функции в базе** по умолчанию получают права вызова. При добавлении любой новой функции нужно сразу ограничить права (`revoke execute ... from public, anon, authenticated`), как сделано для существующих.
